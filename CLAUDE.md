# CLAUDE.md

## Overview

This repo is the Moodle-side plugin for the AI course tutor feature (working name `local_ai_tutor` / `block_ai_privatetutor`). It harvests course content, pushes it to the backend ("Foundry") `/chat` endpoint, renders grounded answers with inline citations back to students, and owns both teacher-facing views (struggle patterns, content gaps) entirely in its own database. The backend does retrieval and grounding in a separate repo — this document covers only the wire contract: what this plugin sends and what it gets back.

## `POST /chat` request shape

**Route**: `POST {foundry_base_url}/api/v1/{tenant_id}/private-tutor/chat`, header `Authorization: Bearer <api_key>` (base URL, tenant ID and API key are pasted into this plugin's admin settings by hand from the Foundry admin UI — there's no self-service provisioning).

**Response is real Server-Sent Events**, not a single JSON body: `Content-Type: text/event-stream`, each frame is a line `data: <json>\n\n`. The SSE frame itself carries no `event:` field — the event name is a `"event"` key inside the JSON. See "Response shape" below for the event sequence.

**Request body** (same JSON shape on every call, `content` only present on the first message of a session):
```
{
  session_id,             // Moodle-generated UUID, created when the chat widget opens
  course_id,
  course_lang,            // ISO 639-1, required on the session's first content-carrying message
  question,
  recent_questions: [...],  // last 3-5 of this session's own question strings, sent on every call
  content: { items: [...] } | omitted
}
```

**First message of a new session** — includes `content`. **Every later message in the same session** — omit `content` entirely; Foundry looks up content already cached for that `session_id` and reuses it. Never resend `content` on a continuing session.

Notes on individual fields:
- **`session_id`**: generated by Moodle (not server-issued), at chat-widget-open time — before any network call, so it survives a failed/retried first request. Track "have I sent content for this session yet" locally in the widget.
- **`course_lang`**: sent only on the first message; governs the language of both answers and practice problems for the rest of that session.
- **`recent_questions`**: Foundry does not persist chat history itself — it relies entirely on this array (sent fresh on every request) to compare the current question against recent ones for stuck-detection.

**Cache-miss fallback**: if the session cache has expired (24h TTL server-side) or `session_id` is unrecognized, the terminal `result` event carries `content_required: true` instead of an answer. On seeing this, resend `content` once to restart the cache. Moodle doesn't need to track the TTL itself — just react to this signal, and always attach `content` fresh on a genuinely new session regardless of any other session's state.

**Error responses** (non-streaming, plain JSON): a 422 body validation error is FastAPI-default `{"detail": [...]}`; an auth failure or any other business-logic/server error is `{"error": "...", "message": "..."}`.

## `content.items[]` format

Each item is one whole citable unit (no chunking/splitting expected on Moodle's side, and none needed by Foundry). Include:

- Course pages, labels, book/wiki chapters
- Resource & file attachments (PDF/DOCX/PPTX/TXT) — **pre-extracted to plain text by Moodle**, not sent as raw files
- Forum posts
- Assignment **descriptions only** — never student submissions
- Quiz **question and feedback text only** — never student answers or grades
- Glossary entries, SCORM package content, `mod_data` entries, H5P activity content, Lesson activity pages, Page course modules

Hard rules:
- **Plain text only** — HTML stripped before sending. Foundry never receives or processes raw HTML or files.
- **No student personal data, ever** — no submissions, no grades, no individual quiz attempts.

## `/chat` response shape (SSE event sequence)

Consume `data:` lines until a `done` or `error` event — **do not stop at `result`**, a `done` bookkeeping event always follows it:

```
data: {"event": "agent_start", "stage": "retrieve", "name": "..."}
data: {"event": "agent_done", "stage": "retrieve", "elapsed_ms": 123}
data: {"event": "agent_start", "stage": "answer", "name": "..."}
data: {"event": "agent_done", "stage": "answer", "elapsed_ms": 456, "tokens": 789}
data: {"event": "agent_start", "stage": "practice", "name": "..."}     // only if the model determines the student is stuck
data: {"event": "agent_done", "stage": "practice", "elapsed_ms": 234, "tokens": 111}
data: {"event": "result", "content_required": false, "in_scope": true, "answer": "...",
       "citations": [{"id": "C1", "title": ..., "url": ..., "confidence": "high"|"medium", "source_type": ...}],
       "connects_to": [{"title": ..., "url": ..., "source_type": ...}],
       "stuck": false, "practice_problems": [...], "primary_citation_id": "C1"}
data: {"event": "done", "total_tokens": 900}
```

On a pipeline exception: `{"event": "error", "message": "..."}` instead of `result`.

Parsing notes (all fields below live **inside** the `result` event's JSON, not at the top level of the response):
- **Inline citation tags** appear inside `answer` as `[C1:high]`, `[C1:medium]`, etc. Confidence is **model-self-reported**, not a computed similarity score — `high` means the model says the claim is directly stated in that excerpt, `medium` means related/inferred. Treat it as a hint, not a guarantee; the model can be wrong about its own confidence.
- The raw model output also has a trailing `RELATED: C3, C5` line and a leading `IN_COURSE`/`NOT_IN_COURSE` sentinel line — both are already parsed/stripped by Foundry before the `result` event is emitted, so Moodle only ever sees the clean `connects_to` array and `in_scope` boolean, never that raw text.
- **`primary_citation_id`** is the highest-confidence citation on the response. Store it (see below) — it's the join key for the struggle-pattern view.
- `practice_problems` is populated only when `stuck: true`; otherwise expect `null`.
- If `content_required: true`, the other fields are null/empty — resend `content` and retry rather than trying to render an answer.

## What this repo owns and must store itself

Persist `stuck`, `in_scope`, and `primary_citation_id` (with title/url/source) from every response, tied to the real `userid` and `courseid`, in this plugin's own table (`local_ai_tutor_turns`). Both teacher views are built from this local table with no further Foundry calls:
- **Struggle patterns**: group by `primary_citation_id`/topic, filter `stuck = true`, count named students per topic over a rolling window.
- **Content gaps**: group stored `in_scope = false` questions (v1: simple text-normalization/fuzzy grouping, done locally).

## Out of scope for this doc

The following live in the Foundry repo and this plugin doesn't need to know their internals: retrieval/ranking logic (lexical keyword-overlap scoring), the `ptutor_session_cache` database schema, and LLM provider/model resolution.
